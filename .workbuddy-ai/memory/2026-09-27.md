### ★ 修复的严重真 bug：直连握手 50% 死锁

- **现象**：`DirectHandshake.Tests` 间歇性"测试宿主进程崩溃"（约 50%），
  并留下 `*_hangdump.dmp`。经查 **9-26 的旧 session 就已经在产生这些 dump**（非本轮引入）。
- **根因**：`DirectClient.ConnectAsync(host, port, peerDeviceId, ct)` 把
  **本机 device_id**（要发给对端做配对校验）和 **对端 device_id**（SIGMA 角色判定用）
  混成了同一个参数。于是客户端用"自己"当对端算角色 → `CompareTo == 0` → 判定为 Responder；
  服务端若也判定为 Responder（当对端 id 字典序更大时）→ **双方都在等 InitiatorHello → 永久死锁**。
- **修法**：`DirectClient` 用 `KeyStore` 派生**本机** id 发给对端，SIGMA 用传入的**对端** id；
  并给直连 SIGMA 加 15s 超时（此前用 `CancellationToken.None`，挂死时无法自愈）。
  测试相应改为传 `ServerDeviceId`。
- **验证**：独立 repro（`/tmp/repro`）连跑 **60 次 TCP-only + 60 次含 QUIC** 全部通过；
  `DirectHandshake.Tests` 全量 **6 连跑 × 13 用例全绿**。

### 顺带修的健壮性问题

- `IRelayTransport.AbortAsync()`（新增，带默认实现）：收尾时**先中断 pending 读**
  （只关底层 socket / abort QUIC 流），等读循环退出后再 `CloseAsync()` 释放 SslStream——
  避免"SslStream.Dispose 与并发 ReadAsync"的 native 崩溃。
  已在 `TcpTlsTransport` / `ConnectedTcpTransport` / `DirectTcpTransport` /
  `QuicTransport` / `ConnectedQuicTransport` / `DirectQuicTransport` 全部实现。
- `DirectSession.CloseAsync()`：把原来的 `_ = Pump.DisposeAsync()`（fire-and-forget）
  改成**可等待且幂等**（缓存 Task）。原写法会让 `StopAsync`/撤销在收尾未完成时就返回，
  随后进程退出与后台释放并发 → native 崩溃。
- `DirectServer.StopAsync`：改为 `await _quicListener.DisposeAsync()`（不再阻塞 `Wait(2s)`），
  且**逐个 await 会话收尾**；QUIC 提前 return 的路径补上连接释放（此前泄漏）。
- `DirectServer` 构造器新增 `enableQuic`（测试可用 `DESKLINK_TEST_DISABLE_QUIC=1` 走纯 TCP）。

- **连带修掉一个测试自身写错的字节**：`PipeServerTests.Oversized_Frame_Disconnects`
  手写 `00 00 A0 00` 是按 LE 写的（LE 下 ≈10MB，确实超限），改 BE 后变成 0x0000A000

  已改为按 BE 构造 100MB，并加 5s 超时兜底（超时 `Assert.Fail` 而不是无限挂起）。
- 教训：**改字节序后必须全局搜"手写字节的测试"**，否则测试自己会变成新的地雷。

### ★ 自测中发现并修掉的 4 个真 bug

1. **拉取路径死锁**：`BeginServePullAsync` 直接在 worker 上 `await RunSenderAsync`，
   而发送循环要等 ack、ack 又由同一个 worker 处理 → worker 永久阻塞在"等 ack"。
   修法：发送循环改到独立 `Task.Run`。
2. **列表响应字节序**：`EncodeListResponse` 用 `BinaryWriter`（默认 **little-endian**），
   而解码端按 BE 读 → 列表项全部错位。这正是本仓库反复踩的字节序坑。
   修法：改用统一的 BE writer。
3. **缺块时发送端白等超时**：接收端发现缺块时回的是 `FileAck`（设计如此），
   但发送端发完 `FileComplete` 后只等 `FileStatus` → 白等 60s 并误判失败。
   修法：`HandleAck` 同时唤醒状态等待者并翻译为"请求补传"。
4. **重复 FileComplete 无应答**：接收端回完最终状态就把传输摘掉；若发送端因并发
   ack 误判为"要补传"而重发 `FileComplete`，接收端已无该传输 → 不回任何东西 → 超时。
   修法：`_lastStatus` 缓存最终状态并幂等应答。

另：把 `FileOpen` 改为**两阶段开启**（接收端先回 accepted 或拒绝）。这不是 bug 修复而是
设计补强——否则"冲突跳过"策略下发送端会先把整个文件传完再被丢弃，用户明确选了跳过却
白白占满带宽。

## 任务小结 10 —— 打通"最后一环"：本地媒体通道（Service 转发泵 + 代理常驻循环）

### 状态
✅ 完成。原 KnownIssues 里"唯一未接通的链路"已闭环。

### 背景：为什么需要一条独立通道

RPC 管道按设计只走元数据、帧上限 64KB；远端画面是几 Mbps 的**流**，绝不能塞进去。
因此另开两条本地命名管道，由 Service 做转发泵：

```
桌面代理 --(AgentMedia 管道)--> Service 转发泵 --(Media 管道)--> WPF 客户端
   ^                                                              |
   +---------------------- 输入事件（反向）------------------------+
```

### 新增

1. `Protocol/Media/MediaChannelContract.cs` 扩展：
   - `FrameType.MediaFlow = 0x3A`（本地专用，Go 不解析）。
   - `MediaFlowPayload{droppedFrames, clientQueueDepth, droppedInput}`。

2. `Service/Media/MediaFrameQueue.cs`（新）：带丢弃策略的队列。
   - `DropOldest`（画面：只要最新的）；
   - `PreferInput`（输入：**优先丢最旧的鼠标移动，绝不丢按键** ——
     丢掉"抬起"会让远端按键永久卡住，比丢一帧画面严重得多）。
   - 单独抽成 public 类是为了**可确定性单测**：管道有 64KB 内核缓冲，
     小帧（鼠标移动 10 字节）要灌满才溢出，端到端制造背压既慢又不稳。

3. `Service/Media/MediaPipeServer.cs`（新）：两条管道 + 转发泵。
   - 画面下行 DropOldest、输入上行 PreferInput、无对端时丢弃不阻塞；
   - 同类连接**后来者顶替**（客户端/代理重启不必等旧连接超时）；
   - 每 500ms 向代理回 `MediaFlow`（丢帧数/队列深度/输入丢弃数）。

4. `Service/Security/PipeAcl.cs`（新）：**修掉一个真实的潜在缺陷**。
   原 ACL 只给 SYSTEM/Admins/CreatorOwner → 服务以 LocalSystem 运行时，
   同机**非提权交互用户根本连不上管道**（Administrators 在过滤令牌里是 deny-only）。
   `--console` 开发模式看不出问题，一装成服务就"控制端连不上服务"且现象是超时。
   现在显式授予**控制台登录用户**；取不到时退回 Authenticated Users 并**记录警告**。

5. `Agent/Runtime/AgentRuntime.cs`（新）：代理**常驻运行循环**（三层结构）。
   - 连接层：断线退避重连；
   - 会话层：一条连接上跑管线；
   - 管线层：帧源 + 编码器，`DXGI ACCESS_LOST` **只重建这一层、不重连管道**
     （重连会让客户端以为会话断了，实际只是显示器模式变了）。
   - 自适应码率闭环：本地编码耗时 + 来自 Service 的丢帧/队列深度/输入丢弃 → 降档。
   - 旋转在 BGRA 阶段做；降档缩放用最近邻；编码器参数变化时重发 `DesktopConfig`。

6. Agent CLI：`--run/--serve`、`--media-pipe`、`--fps`、`--bitrate`、`--max-frames`。
   `--max-frames` 是**有界运行**，专供自检/冒烟（否则只能靠超时兜底，既慢又不确定）。

7. 接线：`ServiceHost` 启动/停止转发泵；`ServiceOptions` 加

   `FATAL: Unable to resolve service for type 'RelayClient'`。
   已改回"注册 null 实例"，并用 `#pragma warning disable CS8634, CS8621` 就地抑制。
2. **命名管道不支持 `ReadTimeout`**（"Timeouts are not supported on this stream"），
   而 `ReadAsync().Wait(ms)` 超时后底层读仍挂着，再发起下一次读会变成**两个并发读**
   抢同一字节流、打乱帧边界。最终改用阻塞读 + 代理 `--max-frames` 有界运行，
   让管道确定性关闭，不需要超时兜底。
3. **record struct 里的 `byte[]` 字段，合成相等是引用比较** ——
   `Assert.Equal(chunk, decoded)` 在内容一致时也会失败，必须逐字段比较。
4. `AddSingleton<RelayClient?>` 这种写法本身就有 CS8634（可空与 class 约束不匹配），
   是"可选依赖"在 DI 里的固有摩擦，无法用类型系统干净表达。

### 顺带清理

## 任务小结 11 —— 补漏：生产路径验证与 5 个真实 Bug 修复

### 状态
✅ 完成。

### 背景
上一段"打通媒体通道"实现了 Service 转发泵 + 代理常驻循环，并通过了冒烟验证。
但冒烟是**手工**启动代理（`--run` + 参数），没有走真实的生产链路：
`客户端点"开始控制" → PipeServer 收到 start_agent → ServiceCore 调用 AgentLauncher → 启动代理`。
于是沿着这条链路排查，发现了 **5 个在生产路径上必然暴露、但在开发/冒烟路径上被掩盖的 Bug**。

### 修掉的 5 个 Bug

1. **AgentLauncher 未传 `--run`**
   `BuildArguments` 漏了 `--run` → 代理跑完一次性自检就退出 → 远程页永远没画面。
   冒烟手工带 `--run`，掩盖了它。修复：强制在 args 第一个位置加 `--run`。

2. **`ArgumentList` 把"开关+取值"拼成单个字符串**
   `$"--pipe {name}"` 传给 `ArgumentList.Add` → 代理收到一个 argv `"--pipe DeskLink.Agent.default"`
   → 匹配不到 `"--pipe"` → "未知参数" → 退出码 1。
   修复：开关和取值必须是**两个独立元素**；`AddOption` 辅助方法 + 单测钉死
   `Assert.All(args, a => Assert.DoesNotContain(' ', a))`。

3. **代理 exe 路径只认同目录（开发布局找不到）**
   `ResolveAgentExePath` 只查 `AppContext.BaseDirectory`，开发时代理在另一个项目目录 →
   走 stub 模式 → 明确日志"not found"但没人看日志以为代理已启动。
   修复：安装路径优先，找不到时按仓库结构回溯 6 级到根目录再探测。

4. **安装脚本只复制 `DeskLink.DesktopAgent.*`（丢了 Vortice DLL）**
   `install.ps1` 用前缀匹配挑文件 → Vortice.DXGI/Direct3D11/MediaFoundation 等 DLL
   名字与代理无关，不会被复制 → 安装后代理启动即 `FileNotFoundException`。
   修复：复制**整个输出目录**（`Copy-Item -Recurse -Force`）。

5. **管道 ACL 未授予交互用户（服务模式下连不上）**
   原 ACL 只给 SYSTEM/Admins/CreatorOwner → Administrators 在过滤令牌里是 deny-only →
   同机非提权用户根本连不上管道 → "控制端连不上服务"且现象是超时（非常难排查）。
   修复：`PipeAcl.Build` 显式授予交互会话用户（`WTSGetActiveConsoleSessionId` → 进程令牌），
   取不到时回退到 Authenticated Users 并记警告。

### 额外改进
- `AgentLauncher` 现在**持续泵取子进程的 stdout/stderr 到文件**：
  不重定向的话子进程继承服务进程的句柄，写满管道缓冲后会被**阻塞在写日志上**，
  表现为"画面莫名卡住"。
- `AgentRuntime` 在帧源不可用（锁屏/无显示器）时抛 `PipelineRebuildException`（而不是普通异常），
  外层只重建管线、**不重连管道** → Service 侧仍看到"代理已连接"，
  客户端显示"等待本地登录"而不是"代理掉线"。
- `ServiceOptions` 新增采集参数（`CaptureMonitorIndex/Rotation/Fps/BitrateBps`），
  由 Service 通过命令行传给代理（代理不读 Service 配置，避免两处漂移）。

### 新增测试
- `AgentLauncherTests` 新增 6 个：
  - `BuildArguments_Always_Includes_Run`（钉死 --run 不变式）
  - `BuildArguments_Includes_MediaPipe_And_NoInject`
  - `BuildArguments_Includes_CaptureParameters`
  - `BuildArguments_Omits_Default_CaptureParameters`
  - `BuildArguments_Inject_Mode_Adds_Inject`
  - `BuildArguments_Never_Combines_Flag_And_Value`（钉死"无空格"不变式）
- 冒烟 `-Mode media` 现在**走生产路径**：`start_agent` → AgentLauncher → 代理带 `--run` 常驻 →
  断言收到 DesktopConfig + 码流分片。
