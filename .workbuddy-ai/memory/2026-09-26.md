### 2. ACL 收紧与"非提升进程"的冲突（重要设计决定）

`FileSystemAcl.LockDownDirectory/File` 会把 ACL 收紧为 SYSTEM+Administrators 并
**删除继承**。生产路径（服务以 LocalSystem 跑）没问题，但 **--console 开发模式与
单测以普通用户跑**，收紧后调用者自己就失去写权限 → 后续写 keystore.json 直接
`UnauthorizedAccessException`（曾导致 Service.Tests 11 项失败）。

解决：收紧前先做**实测探测**（在临时子目录/临时文件上真正应用同一 ACL 并试写），
写不了就跳过收紧并返回 `Applied=false, SkippedReason="caller-loses-write-access"`。
不削弱生产安全性（LocalSystem 必然能收紧），只保住开发/测试可用性。
探测用实测而非 `IsInRole(Administrator)`：UAC 拆分令牌下角色判断 ≠ 能否写目标目录。

### 3. 协议字节序（本次最关键的修复）

**约定：多字节整数一律 big-endian**（`src/vps/internal/proto/proto.go` 编码总原则；
C# `HandshakeMessages` 也用 BigEndian）。

但 C# `FrameCodec`（u16 payloadLen）与 `MuxFrame`（u32 len）用的是 little-endian，
与 Go 全部 big-endian 冲突。**两端各自的自测都能过**（都只测自身往返），
所以这个互通级 bug 一直没有暴露。已把 C# 两处改为 big-endian。

**教训：跨语言协议必须有"黄金字节串"锚点，往返自测无法发现字节序分歧。**
新增 `src/vps/internal/proto/crosslang_golden_test.go` 作为唯一权威锚点，
与 C# `E2EAlignmentTests` 的固定 hex 一一对应。

### 修掉的三个真 bug（都会在 P4/P5 暴露）

1. **Go relay 双泵乱序**（`wiring.go` + `server.go`）：
   两端各自 Dial 时，早期实现会让**两条 serveSession 各起一个双向泵**，同一条连接被
   两个 goroutine 并发读 → 字节乱序 → 破坏 E2E 严格递增的 AEAD 计数器（解密失败）。
   修法：`Wire` 返回 `newlyWired`；只有“先到者”起泵；后到者 `SignalDialGate` +
   `WaitUnwired`（保持连接存活但**不读数据**）。新增 `dialGate` / `sessionEnd` 两个
   一次性信号，`Unregister`/`KickDevice`/被顶替时统一唤醒。
2. **Go relay 跨 goroutine 写同一连接**（`server.go` + `wiring.go`）：
   早期 `tryWire` 由**先到者的 goroutine** 代发 PeerEvent(Ready) 给对端，与对端自己的
   DialResult 写并发 → 顺序不保证 → 客户端可能把 Ready 当业务数据处理
   （QUIC E2E 偶发 `A got "\x05\x00!\x03..."`）。
   修法：Ready 改由**每个会话自己的 goroutine** 在 DialResult 之前写
   （`writeReadyThenDialResult`）；并删除 `notifyPeerOfflineLocked`
   （跨 goroutine 写泵中的连接），对端靠“连接关闭”感知下线并重连。
3. **Service 不是可执行程序**：`DeskLink.Service.csproj` 缺
   `<OutputType>Exe</OutputType>` → 默认 Library → 不生成 `runtimeconfig.json` /
   入口，`Program.Main` 根本起不来（console 双实例、Windows 服务注册、P10 installer
   全受影响）。已补上（用 `Exe` 而非 `WinExe`，console 模式要 stdout 日志）。
   注意：csproj 的 XML 注释里不能出现 `--`（MSB4025）。

  （结构体里叫 `Legacy*`，用 `issuerDeviceIDHex()` / `redeemerPubKeyHex()` /
  `issuerPubKeyHex()` 三个访问器做"新名优先、旧名回退"）。
- **提前校验两端公钥都已注册**：把原来的 500 变成可操作的 400，并在 message 里
  明说"this field takes the Ed25519 public key, not the device_id"。
- issue 也加了"出码端必须已注册"的校验（否则码发出去没人能领）。
- 新增 3 个回归用例：`TestPairingCodeRedeemWithDeviceIDReturns400`、
  `TestPairingCodeIssueUnregisteredDeviceReturns400`、
  `TestPairingCodeRedeemLegacyFieldNamesStillAccepted`；`TestRateLimit_RedeemByCode`
  刻意保留旧字段名，顺带覆盖兼容路径。

### 2. Ping RTT 是假的（恒为 0）—— 已改为真实测量

`SessionPump` 的 Ping/Pong 现在带时间戳：
payload = `[u64 seq BE][u64 sendUnixMicros BE]`（16B），**接收方原样回显**，
发送方用回显值算 RTT（只解读自己的时间戳，因此不依赖两端时钟同步）。

### 5. 又发现一个 relay 真 bug：旧连接的清理会误删新会话

现象：`-Mode all` 下 TCP 用例连续 25s 失败，两个实例互相报 `peer_offline`。

根因：`Wiring.Unregister(deviceID)` **无条件**删除表项。A 断线重连时
（conn1 退出、conn2 已注册），若 conn1 的清理晚于 conn2 的注册，就把 conn2 的
表项一并删掉 → 对端永远查到 peer_offline → 双方不断重连又互相删除，**永不收敛**。
触发条件：两端几乎同时启动时先到者必然撞 peer_offline → 客户端断开重连 →
进入上述互相删除循环。

修法（两处，缺一不可）：
- `wiring.go`：`Unregister(deviceID, c Conn)` 增加守卫 —— 只有 `e.Conn == c`
  才移除；已被新连接顶替时什么也不做。`server.go` 的 defer 相应带上 `c`。
- `E2ESessionHost.ControlHandshakeAsync`：`peer_offline` 时**在同一条连接上重试
  Dial**（15 次 × 400ms），不再断开重连。relayd 本来就是这个设计
  （"不立即断：让客户端自己决定重试"），客户端此前却直接放弃，导致无谓的连接抖动。

回归测试：`TestWiringStaleUnregisterKeepsNewSession`、
`TestRelayTCPDialRetryAfterPeerOffline`（先 dial 撞 peer_offline，再接入对端，
同一连接重试成功并密文互通）。

## 深度复查：又找出并修掉 9 个问题（含 1 个静默数据损坏 bug）

复查范围：P1~P5 全部已完成代码（Go relay/proto/regapi + C# Protocol/Service）。
结论：**发现 1 个严重静默数据损坏 bug（Go+C# 同源）、2 个可被对端触发的资源耗尽、
3 个关闭/生命周期缺陷、3 个语义与文档不符**。全部已修并补回归测试。

### ★ 最严重：帧长度字段 u16 溢出 → 静默截断 → 整条流错位（Go + C# 同源）

`EncodeFrame`(Go) / `FrameCodec.Encode`(C#) 只校验 `MaxFramePayloadSize`(256KB)，
但帧头长度字段写的是 `uint16(len(payload))` / `(ushort)payload.Length`。
于是 65536..262144 的负载会**回绕**长度字段，payload 字节却全量写出。

实测（探针）：70000B 负载 → `EncodeFrame` 无错、编码出 70003B；
`TryDecodeFrame` 读到 `len=4464`、只消费 4467B，**剩余 65536B 全部错位且不报错**。
两侧逻辑一致，所以跨语言黄金向量也测不出来（两边错得一样）。

修法：新增 **`MaxFramePayloadWireSize = 65535`**（u16 决定，两侧同名同值），
`EncodeFrame`/`Encode` 改为校验它并抛可判定的错误（Go `ErrFramePayloadTooLarge`）。
`MaxFramePayloadSize` 保留为"缓冲区/DoS 保护上界"并改写注释说明二者关系
（需要更大负载必须上层分片，DESIGN.md 的 FileChunk/DesktopVideo 分片语义本就如此）。
回归测试：Go `TestEncodeFrame_Uint16WireLimit`、C# `Encode_PayloadOverUint16WireLimit_ThrowsInsteadOfTruncating`
+ 边界值 65535 必须可往返。

### 可被对端触发的资源耗尽（C# SessionPump.TryExtract）

1. `len == 0` 时只 `return false` → 同一个非法前缀被反复解析，接收缓冲**无限增长**
   （对端一句话就能吃光内存）。
2. `len` 超上界时 `_pendingBuffer.Clear()` 后继续 → 长度前缀已被消费，后续字节被当成
   新帧头，**流永久错位且不报错**。
   修法：两种都改为**终止会话**（`_cts.Cancel()`），与 Dispatch 解密失败一致。
3. 顺带修：`maxOuter` 少了内层帧头的 3 字节（`1+8+MaxFramePayloadSize+16`），
   会把"最大合法帧"误判为超大帧；改为从线上上限推导。

### 关闭 / 生命周期缺陷

4. **Go `Server.Run` 不响应 ctx**：早期把 `acceptTCP` 放在当前 goroutine 阻塞，
   而 `Close()` 在 `<-ctx.Done()` 之后才调 → 只 cancel ctx 会永久卡在 Accept。
   cmd/relayd 恰好 cancel 与 Close 都调了，所以被掩盖。已改为"ctx 取消即关监听 +
   两个 accept 循环都放后台 + `wg.Wait()` 收尾"。
5. **Go transport 不监听 ctx 取消**：`streamConn.Recv` 只设 `SetReadDeadline`，
   覆盖不了"被 cancel"（要等 45s 读超时才醒）→ 关闭时收尾被拖几十秒。
   改用 `context.AfterFunc` 把取消映射为"立刻到期"的读超时；`quicConn.Recv`
   同时补上 `ctx.Deadline` 支持（此前无条件 45s）。
6. **C# `SessionPump.DisposeAsync` 不幂等**：第二次进来对已释放的 `_cts` 调 `Cancel()`
   → `ObjectDisposedException`。加了 `Interlocked.Exchange` 守卫。
   （这个 bug 是新写的 framing 测试直接撞出来的。）

### 语义与文档不符

7. **Go 每 IP 限速只覆盖握手窗口**：`handleTCPConn` 在 TLS 握手后就 `Release`，
   于是 `MaxConnPerIP` 实际只限制并发握手数，在线连接数不受控；且 **QUIC 路径完全没限速**
   （而 QUIC 才是默认优先的传输）。改为名额持有到会话结束，并给 QUIC 也加上。
8. **C# 退避在握手前就被重置**：`RelayClient` 连接成功即 `_backoff.Reset()`，
   于是"连上了但会话一直建不起来"（未配对/对端始终离线）会每次都把退避打回第一档
   → 约 1 次/秒的无限重连风暴。改为 `OnReady` 返回 `bool`（本次传输是否建立过会话），
   只有 true 才重置。
9. **C# 握手/SIGMA 无超时**：传输层 `ReceiveAsync` 只受 ct 约束，relay 若"接受连接
   但不回应"，客户端会永久卡住且重连循环永不触发。新增 `ControlHandshakeTimeout=20s`
   与 `SigmaTimeout=15s`，并区分"超时"与"外部取消"两种状态。
